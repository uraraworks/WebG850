## 底本と、その信用度

**底本は公式マニュアルではない。** 当初の予定（`資料リンク集.md`）では日本語版取扱説明書を
使うつもりだったが、archive.org のアイテムは dark 化されておりファイル一覧すら返らない。
英訳 PDF のホスト（basic.hopto.org）は応答しない。実際に入手できたのは以下：

> Sharp PC-G850V(S) Bedienungsanleitung
> Jörg Wrabetz 編、v1.3（2017-12）、375 ページ
> https://github.com/anton-tchekov/sharp-pc-g850v

編者自身が「シャープ純正の資料ではない。旧機種の純正マニュアル群をベースに、
ネット上で集めた情報も加えたもの」と明記している**第三者編纂のドイツ語資料**。
第13章「BASIC KOMMANDO LEXIKON」（p.182-252）が命令リファレンス本体。

### これはクリーンルーム方針に反しないか

反しない。抽出したのは**命令名・書式・引数の型と範囲・返り値・エラー条件**という
インタフェース仕様＝事実であり、ROM でも逆アセンブルリストでもない。
BASIC の命令体系は取扱説明書として公開された利用者向けインタフェースそのものである。

ただし**底本の散文は一切コピーしていない**。`summary` は全て日本語で書き起こした。
`basic_errors.yaml` には当初ドイツ語の解説文が逐語で入っていたが、
エラー識別子ではなく著作物としての解説文なので削除した（実機が表示するのは番号のみ）。

### 数値の細部は信用しないこと

底本は OCR された PDF で、**誤認が実在する**。確認済みの例：

- `1O:DEGREE`（行番号 10 の `0` がアルファベット `O`）
- `ACS(O)`、`arcoos`
- `≤` が `s` に化けた範囲表記（`-1 s X s 1`）
- `SQU x²` の上付き 2 が落ちて `SQU x2`

疑わしい箇所は `ocr_suspect: true` を立ててある。当初は9件（ACS, ASN, CIRCLE, DEG,
DELETE, DIM, EXP, PRINT->LPRINT, VDEG）だったが、英語版マニュアルでの再検証により
8件は独語側のみのOCR起因と確認できて解除した。**現在残っているのは CIRCLE の1件のみ**
（範囲記述「0-360」が独語版自身の実行例と矛盾しており、OCR誤認ではなく記述内容そのものの
食い違いのため。詳細は「実測が必要なもの」節を参照）。きれいに直したように見せていない。

**したがって、この仕様書は「実装の骨格」としては信用してよいが、
定数・境界値・誤差挙動は公式資料か実測で裏を取る層として扱う。**
日本語版マニュアルが入手できたら差分照合したい。

### 底本の権利状況（重要）

ドイツ語版 v1.3 の権利表記に、編者自身がこう書いている：
「本マニュアルはシャープ純正ではない。ただし旧機種のシャープ純正マニュアル群を基に
作られているため、**本マニュアルの配布はシャープ社の許諾を条件とする。その許諾はまだ得られていない**」。

一方、英訳・改訂版である英語版 v3.0（Jack W. Hsu 編、2018-09）ではこの一文が消えており、
`Copyright © 2018 Jack W. Hsu` と「非営利ならPDF利用・ネット公開は自由」だけが残っている。
元資料の権利主張が引き継がれず、編者自身の著作権表示に置き換わっている構造。

つまりグレーの正体は「archive.org から取得したこと」ではなく**資料そのものの出自**であり、
ダウンロードの有無に関係なく残る。ただし本仕様書が抽出したのは命令名・書式・引数・返り値という
インタフェースの事実であり、底本の散文は一切転記していない（前節と同じ整理）。

### 公式資料の入手可能性（調査済み）

- シャープ公式の製品ページは生きているが説明書へのリンクは無い。電卓サポートのURLは404
- 国立国会図書館サーチでのヒットは2件のみでマニュアルは無し。
  うち1件は村山健一「教育用ポケットコンピュータPC-G850とその応用」（1997年、ナガイ）
- archive.org の日本語版マニュアルは、**別コピー（`pc-g-850-vs-manual_202308`）も `is_dark: true`**。
  同一資料の複製が2つとも落とされ、ファン編纂の英語版だけが残っている。
  権利者からの申し立てを強く示唆する（理由は開示されないので断定はしない）
  → archive.org 経由で日本語版を追うのは筋が悪い。実機付属の現物を当たるほうが早い

### ドイツ語版の出所が確認できた（著者本人サイト）

ドイツ語版マニュアルは、**著者 Jörg Wrabetz 本人のサイトでも配布されている**ことが判明した。

- `https://wrabetz.com/computer/resources/Sharp_PC-G850_VS_manual_german.pdf`
- 手元のファイル（`anton-tchekov/sharp-pc-g850v` 経由で取得）と**同一ファイルであることを
  検証済み**。サイズ 19,119,756 バイトが一致し、先頭・中間・末尾の3箇所を Range リクエストで
  ハッシュ照合して全一致した（ファイル自体はダウンロードせずに確認）
- インタフェース仕様書も同じ場所にある：`.../Sharp_PC-G850VS_Interface.pdf`（2.6MB、未読）
- これにより「第三者のミラー経由」ではなく「著者本人の配布物と同一」と言えるようになった。
  **ただし著者自身が「シャープの許諾を得ていない」と書いた構造は変わらないので、
  `verified_by` は `manual_3rd_party` のまま**
- サーバの `last-modified` は2017年5月で、PDF内の版表記「12/2017」と食い違うが、
  インタフェース仕様書も3秒違いの同時刻を示している。**サーバ移行時の一括コピーと見るのが
  自然で、版が古いことを示すものではない**

### 英語版を底本に加えたこと

Jack W. Hsu 編、v3.0、2018-09、英語。ドイツ語版 v1.3 の英訳・改訂版。

- 同一系譜なので内容の誤りは共通して残るが、**スキャンとOCRは別物なのでOCR誤認は独立する**
- 付録が A〜M（ドイツ語版は A〜L。スピーカー増設が追加）
- ドイツ語版では画像埋め込みで読めなかった**付録H（文字コード表）が英語版ではテキストで入っている**
  （字形のOCRなので精度は要確認。「残っている穴」参照）

## 実測が必要なもの

英語版マニュアル（Jack W. Hsu 編, v3.0, 2018）でドイツ語版と突き合わせた再検証記録は
`spec/_reconcile_en.md`。**同一系譜（英語版は独語版の英訳・改訂）の資料同士で内容そのものが
食い違う例が3件見つかった**のが今回いちばん重要な発見。英訳・改訂の過程で入った差なので、
どちらが実機の挙動かは資料だけでは決まらず、実測でしか決着しない。

### 最優先：両版で食い違った3件（実測対象）

- **CIRCLE** — 開始角・終了角の範囲。独語版は「0-360」と明記するが、英語版は「-360〜360」と
  明記した上で符号の意味まで説明する（負値は原点から半径線を引いて扇形になる、正値は弧のみ）。
  両版共通の実行例 `CIRCLE(71,23),20,-45,-135` は独語版自身の「0-360」という記述と矛盾しており
  独語側の誤記の可能性が高いが、実機が実際にどの範囲を受理するかは実測しないと断定できない
- **REC** — 直交座標変換の結果の割り当て。本文は両版とも「x軸からの距離・y軸からの距離を
  予約変数 Y・Z に割り当てる」と書くが、英語版の実行例の注記をそのまま読むと
  「関数値=x座標、Z=y座標」で本文と正反対になる。POL は本文と実行例が一致している
  （Y=r, Z=θ）ので、REC だけ本文と実行例が食い違うのは不自然
- **RANDOMIZE** — 種の再現性。英語版は「既定の種は電源投入ごとに同一（デバッグに便利）、
  RANDOMIZE で新しいランダムな値にリセットされる」と明快に説明する。ところが独語版の実行例は、
  RANDOMIZE を置いたうえで電源 OFF→ON して RUN し直しても乱数列 (2,1,10,8,10) が
  寸分違わず再現している。種の決定要因は両版から確定できない

### needs_measurement（5件）

| 命令 | 理由 |
|---|---|
| `CLOAD` `CSAVE` | 中間コード表にのみ存在。カセット命令で **G850V/VS には機能自体が無い**（G850/S 専用）。phase 3 |
| `HDCOPY` `SPINP` `SPOUT` | 中間コード表にのみ存在。両版とも本文に記載なし（英語版でも確認済み） |

いずれも `verified_by: none`。`NOT` はここから外れた（下記「解決済み」参照）。

### 解決済み：NOT はビット反転と確定

`AND` `OR` `XOR` は 5.11 節の記述から **16bit 2の補数のビット演算**と確定できていたが、
`NOT` だけが単項演算子のため独語版の記述だけでは決まらなかった。
英語版 5.4.4 節に AND/OR/XOR/NOT のビット単位真理値表が実際の 0/1 値付きで収録されており、
**単純な全ビット反転（`NOT X = -(X+1)`）と確定した。** needs_measurement から外し
documented に引き上げ済み。

### partial（6件）— CIRCLE, DEG, LIST, MID$, RANDOMIZE, REC

- CIRCLE / REC / RANDOMIZE は上記「最優先」参照
- `LIST` `MID$` — エラー発生条件は書かれているが ERROR 番号が両版とも本文に無い
- **`DEG`** — hh の上限が両版で同一の形で途切れている（`0 to …`）。
  **独立にOCRされた両版で同一の欠落なので、OCR誤認ではなく原著自体が上限を明記していないと
  判断した**（`ocr_suspect` は解除、ただし上限は未確定のため status は partial のまま）。
  この「両版一致の欠落＝原著側の欠落」という判断は、単独資料では区別できない
  OCR誤認と原著の記載漏れを切り分ける手法として今後も使える

## 中間コード表との突き合わせ（重要）

**独立した第2の情報源（akiyan.com の中間コード表 141件）と突き合わせた。**
突き合わせ前に HTML の `<table>` を Python で直接パースし、テキスト化で列がずれないようにした。
生成後、別実装で再パースして 141/141 の完全一致を確認している。

この突き合わせで、**目次照合をすり抜けた抽出漏れ 3 件（`HSN` `HTN` `MDF`）が見つかった。**
目次には載っているのに項目ごと欠落しており、単一資料の内部整合チェックだけでは
最後まで気づけなかった。詳細は `spec/_crosscheck.md`。

### 分かったこと

- **G850 BASIC は 1バイトトークンで足りている可能性が高い。**
  トークン 141件に対し命令 136件。トークン側にしか無いものは全て説明がつき、
  命令側にしか無いもので未解決なのは実質 `AUTO` 1件だけ
  （`BLOAD M` `BLOAD ?` 等はマニュアルが引数違いを別項目にしているだけで、
  実トークンは共通1個と考えるのが自然）
- **中間コード表の出自が G850S であることの傍証が取れた。**
  カセット命令 `CLOAD` `CSAVE` のトークンが存在するが、V/VS のマニュアルには記載が無い。
  カセット機能が G850/S のみという前回調査の結論と符合する
- トークン表側の `POIPUT`（0x49）は誤記。本文・目次とも一貫して `PIOPUT`

## 残っている穴

1. **文字コード表はテキスト化できたが精度未確認。** ドイツ語版 v1.3 の付録 H は画像埋め込みで
   機械可読テキストが無かったが、英語版 v3.0 の付録 H（同じ位置づけ）はテキストで入っている。
   ただし字形の OCR なので誤認の可能性は他の数値項目と同様に残る。
   フォントは自前で打ち直す方針なので急がないが、文字コード ⇄ 字形の対応の裏取りに使える
2. **`AUTO` のトークンが未特定**
3. **公式（日本語）マニュアルとの差分照合が未実施**
4. **実作品での使用頻度が未集計。** 実在作品276本を機械解析した結果（調査記録は未公開）では
   現行投稿シーンの54%が動く見込みが出ているが、phase 1 の 102 件のうち、
   どれを先に作れば何%動くかという命令単位の内訳はまだ数値化できていない。
   数値化できれば**実装順の決定に一番効く**
5. **インタフェース仕様書（`Sharp_PC-G850VS_Interface.pdf`、2.6MB）が未読。**
   シリアル転送・ROM吸い出しの経路を作る段になったら読む

## 次にやること

実機購入の見通しが立った（中古で1万円台〜2万円弱）。型番は PC-G850V または PC-G850VS、
取説付きの個体を狙う。11ピンのシリアルケーブルが別途必要。実機が入れば `verified_by` を
`manual_official` / `hardware` に上げられ、partial 6件と needs_measurement 5件がまとめて動く。

1. **食い違い3件（CIRCLE / REC / RANDOMIZE）の実測が最優先。**（`NOT` は解決済みのため対象から外れた）
2. 実作品での命令使用頻度を集計し、phase 1 の 102 件に実装順をつける
3. Phase 1 プロトタイプ着手。`status: documented` かつ `phase: 1` の 96 件が即着手範囲
4. `basic_errors.yaml` のエラー番号を、各命令の `errors` フィールドに紐付ける
   （現状 `errors` が埋まっているのは 10 件程度）
